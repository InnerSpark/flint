# Contributing

## The path for anything new

1. **File an ASDS ticket** describing the need.
2. **Reuse first.** Build only when no token or component fits.
3. **Token first.** Add or change tokens before touching any component.
4. **Every state,** with an accessibility note.
5. **Check it here.** Walk the component in this workbench: every state, light and dark, both densities, keyboard only.
6. **Release.** Bump the version, add a changelog entry, tag the release.

## What the build checks

| Check | What fails it |
| --- | --- |
| Contrast | Any text pair under 7:1, or any control edge, focus ring or chart color under 3:1, in either mode |
| Usage | A control drawn with a decorative border, or a density that shrinks a control or target |
| Parity | Any platform (CSS, MUI, shadcn, Swift) landing on a value tokens.json did not give it, or a hardcoded color in the MUI theme |
| Workbench | Any axe violation on any page in light or dark, or a token with no row on its page |

Run them with `npm run build` in the repo root, and `npm run build && npm run verify` in `workbench/`.

## Versioning

Flint uses semver, independent of the apps that consume it. A new token or component is a minor. A value fix is a patch. A rename or removal is a major. Deprecated tokens keep working for one minor cycle, then go in the next major.
